# Whisk — M4 Voice Channels and Audio Controls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver permissioned low-latency voice rooms with device management, mute/deafen, push-to-talk, optional local noise processing and tested reconnect behavior.

**Architecture:** Backend owns room authorization and temporary grants; a client media engine wraps LiveKit and a native audio engine. State visible in GPUI is driven by media events and backend channel permissions.

**Tech Stack:** Rust/Axum, LiveKit Rust SDK, Tokio, CPAL/native devices as feasible, GPUI.

**Spec:** `docs/superpowers/specs/2026-10-24-media-design.md` (read with `docs/prd.md`)

**Status:** Planned, not executed. These paths/signatures are proposed; reconcile them with the pinned toolchain and real repository before implementing.

## Global Constraints

- One active voice room per client across all instances.
- Check CONNECT_VOICE, SPEAK and publishing rights before granting any media access.
- Self-hosted LiveKit stale token window is known; short TTL and participant removal mitigate but do not guarantee immediate credential revocation.
- Noise processing remains local and selectable; echo cancellation needs reference audio.
- Prefer task-by-task test-first behavior, red → green → refactor → small commit; never mark tests passing without executing them.

## Review Focus

- Wrong-instance room token must be denied (Task 1).
- Unplugged microphone must not freeze UI (Task 2).
- Joining a second room must cleanly leave the first (Task 3).
- Muted user cannot publish audio even if old UI state says unmuted (Task 4).
- Ban must revoke backend grant and remove active participant (Task 5).
